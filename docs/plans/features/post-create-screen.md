# 機能実装方針: 投稿作成画面

確認の種類: [確認済]=コードで確認 / [提案]=本方針の提案 / [未確認]=実環境で未確認(実装前に確認する)

## Context

`/post`(投稿作成画面)はロジックだけが実装済みで、見た目は素のHTMLのまま。image.png の画面構成(背景の上に中央の半透明パネル、タイトル・本文入力欄・タグ・投稿ボタン)に合わせて作り替える。あわせて、監査レポート(`docs/examination/audit-report.md`)で指摘済みの二重送信(M3)・文字数上限なし(H3)を、この画面の範囲で解消する。

## 1. 機能の概要

- ログイン中のユーザーが、本文(最大500文字)と任意個のタグを指定して投稿する画面。Header の「投稿する」から遷移する。
- 画面構成(image.png): 中央に半透明の明るいグレーの角丸パネル。上から、タイトル「投稿作成」/ 本文入力欄(大きめ)/ タグ選択(横並び)/「投稿」ボタン(中央)。
- 上部ナビは既存 Header をそのまま使う(変更なし)。

### 現状の確認

- [確認済] `app/post/page.tsx` に、タグ取得・タグ選択・`posts` 登録 → `post_tags` 登録・ホームへの遷移まで実装済み。**ロジックは再利用でき、差分は見た目と下記の不足分**。
- [確認済] 不足: 二重送信対策なし(ボタンはタグ読み込み中のみ無効)/ 文字数上限なし / 通知がすべて `alert()` / 未ログインは投稿ボタンを押すまで分からない。
- [確認済] `lib/tags.ts` の `fetchTags()`、`lib/types.ts` の `Tag` を使用中。そのまま再利用する。
- [確認済] `posts.content` は `text not null` のみで、DB側に空白のみ禁止・長さ上限の制約がない(`DATABASE.md` §3.2)。
- [確認済] RLS は文書上、`posts` の INSERT が `auth.uid() = user_id`、`post_tags` の INSERT が「対象投稿の投稿者本人」(`DATABASE.md` §5)。
- [確認済] コメントの上限は `app/post/[id]/page.tsx` の `MAX_LENGTH = 500` と `入力数/500` のカウンター表示。
- [確認済] `.app-main` は `overflow-y: auto` で、パネルが画面より高くてもスクロールできる。
- [確認済] プロフィール画面(`app/profile/page.tsx` + `.profile-card*`)が「中央パネル+パネル内メッセージ+状態表示(読み込み中/未ログイン)」の前例。構成はこれに揃える。

## 2. 実装方針

**既存 `app/post/page.tsx` を改修し、`app/globals.css` にパネル用スタイルを追加する。新規ファイル・新規コンポーネント・新規ライブラリなし。**

| 論点 | 採用 | 見送った案と理由 |
|---|---|---|
| 画面の作り方 | 既存ページを改修 | Server Action化・フォームのコンポーネント分割: 前例がなく1画面専用のため過剰 |
| 文字数上限 | 500文字(コメントと同じ) | 1000文字 / 上限なし |
| タグUI | ホームと同じピル型ボタン(`.home-tag-button` を再利用) | 画像どおりのチェックボックス: 見た目をホームと統一するため不採用 |
| DB変更 | `posts.content` に CHECK 制約のみ追加 | 変更なし: API直接呼び出しで制限を回避できる / RPCで一括登録: 前例がなく変更が大きい |
| 通知 | パネル内メッセージ。成功時は通知なしでホームへ遷移 | `alert()` 維持: プロフィール画面の方式と揃わない |

上表の採用案はユーザー回答済みの確定事項。

## 3. 具体的な設計・実装方法

### 3.1 画面構造 [提案]

```
section.post-form
  h1.post-form__title            投稿作成
  textarea.post-form__input      本文(maxLength 500・placeholder は現行文言を維持)
  p.post-form__count             0/500(入力欄の右下)
  div.post-form__tags            タグ(横並び・折り返し・中央寄せ)
    button.home-tag-button       タグ名(選択中は .active、aria-pressed を付与)
  div.post-form__footer          (中央寄せ)
    button.post-form__submit     投稿 / 投稿中...
  p.post-form__message           エラー表示(必要時のみ)
```

- 状態表示(読み込み中・未ログイン)は `section.post-form.post-form--state` として同じパネル内に中央表示する。未ログイン時は「ログインしてください」と `/login` へのリンク(プロフィール画面と同じ形)。
- 現行の `<h2>タグ</h2>` 見出しと `<br />` は画像にないため削除する。
- タグが0件・タグ取得失敗の場合は、タグ欄に短い文言を表示するだけにする(タグは任意なので投稿は可能なまま)。
- 「キャンセル/戻る」ボタンは追加しない(画像になく、Header から移動できる)。

### 3.2 ロジック(既存を維持しつつ追加)

- **定数**: `MAX_LENGTH = 500` をファイル先頭に定義(`app/post/[id]/page.tsx` と同じ書き方。1箇所ずつのため共通化はしない)。
- **state 追加**: `userId`(ログイン判定用)、`submitting`(二重送信防止)、`message`(パネル内表示)。
- **初期表示**: `supabase.auth.getUser()` でログイン確認 → 未ログインなら状態表示で終了。ログイン済みなら `fetchTags()`。
- **タグ選択**: 既存の `handleTagChange` と `selectedTagIds` をそのまま使い、入力要素だけ checkbox からボタンに変える。
- **投稿処理**(`handlePost`):
  1. `submitting` 中は何もしない。
  2. `content.trim()` が空ならメッセージ表示。501文字以上もメッセージ表示(`maxLength` の保険)。
  3. `submitting = true`、メッセージをクリア。
  4. `auth.getUser()` を再取得し、`user_id` には必ずこの値を使う。
  5. `posts` に INSERT(`.select("id").single()`)。
  6. タグ選択があれば `post_tags` に INSERT。
  7. 成功したら `router.push("/")`。
  8. 失敗時は `submitting = false` に戻し、入力内容は保持する。
- **タグ登録だけ失敗した場合** [提案]: 登録済みの投稿を `posts` から DELETE して取り消し、「投稿に失敗しました。もう一度お試しください」と表示する(入力は残るので再試行できる)。取り消しの DELETE も失敗した場合のみ「投稿は保存されましたが、タグを設定できませんでした」と表示し、再投稿による重複を防ぐため投稿ボタンを無効のままにする。
- **エラー文言**: Supabase の `error.message` は画面に出さず `console.error` に出力する。画面には固定文言を表示する。CHECK 制約違反(`error.code === "23514"`)は「投稿内容は500文字以内で入力してください」。
- ボタンの無効条件: `submitting` または本文が空(trim後)。

### 3.3 スタイル(`app/globals.css` に `.post-form*` を追加)

- パネル: `max-width: 420px`・中央寄せ・角丸16px・上下に余白。背景は**半透明の明るいグレー**(画像準拠。目安 `rgba(217, 217, 217, 0.6)` + `backdrop-filter: blur`)。文字色は濃色(`#1e293b`)。`.profile-card` は不透明のため流用せず、値だけ揃える。
- タイトル: 中央寄せ・22px前後。
- 本文入力欄: パネル幅いっぱい・高さは画像に合わせ大きめ(目安 `rows={12}`)・`resize: none`・白系の背景に濃い文字。フォーカス時の枠は `.profile-card__field` の指定に合わせる。
- カウンター: 小さい文字で右寄せ。
- タグ: `display: flex; flex-wrap: wrap; justify-content: center; gap`。ボタン自体は既存 `.home-tag-button` / `.active` をそのまま使い、新しいボタン用CSSは書かない。
- 投稿ボタン: 中央寄せ。配色は `.profile-card__save` に合わせる(濃色背景・白文字・`:disabled` で薄く)。
- `@media (max-width: 600px)`: パネルの余白を詰めて画面幅に収める。
- Header・背景・`.app-main`・他画面のクラスは変更しない。

## 5. データベースへの変更

`posts.content` に CHECK 制約を1つ追加する(Supabase の SQL Editor で実行)。テーブル・カラム・RLS の追加変更はなし。

```sql
-- 事前確認: 違反する既存行がないこと(0件であること)
select id, char_length(content)
from posts
where char_length(content) > 500
   or btrim(content, E' \t\n\r　') = '';

-- 制約の追加
alter table posts
  add constraint posts_content_check
  check (
    char_length(content) <= 500
    and btrim(content, E' \t\n\r　') <> ''
  );
```

- [未確認] 実DBに違反行があると `alter table` が失敗する。その場合の扱い(該当行の修正・削除、または `not valid` を付けて新規分だけ検証)は、件数を見てから決める。
- [未確認] 実DBの RLS が `DATABASE.md` の記載どおりか(`posts` INSERT / DELETE、`post_tags` INSERT)。3.2 の「取り消し DELETE」は `posts` の本人 DELETE ポリシーに依存する。

## 6. 処理フロー

1. `/post` を表示 → `auth.getUser()`
2. 未ログイン → パネル内に「ログインしてください」+ ログインページへのリンクを表示して終了
3. ログイン済み → `fetchTags()` でタグ一覧を取得して表示
4. 本文を入力(カウンター更新)、タグを任意で選択/解除
5. 「投稿」押下 → 検証(空・500文字)→ ボタンを無効化
6. `auth.getUser()` 再確認 → `posts` に INSERT → 投稿IDを取得
7. タグ選択あり → `post_tags` に INSERT
8. 成功 → ホーム(`/`)へ遷移
9. 失敗 → パネル内にメッセージ表示、ボタンを再び有効化(入力は保持)。タグ登録のみ失敗した場合は投稿を取り消してから同様に表示

## 7. 実装後の確認・テスト項目

- 画像と見比べて、中央パネル・タイトル・入力欄・タグ・投稿ボタンの並びが合っている。
- タグがホームと同じピル型で表示され、選択/解除・複数選択ができ、選択中が見分けられる。
- 本文のみ(タグなし)で投稿でき、ホームの先頭に表示される。
- タグ付きで投稿すると、ホームのカードと投稿詳細にタグが表示される。
- 空欄・空白のみでは投稿できない。501文字目が入力できず、カウンターが `500/500` で止まる。
- 投稿ボタンを連打しても投稿が1件だけ作られる。
- 未ログインで `/post` を開くとログイン案内が出る。
- 通信エラー時(開発者ツールでオフライン)にパネル内へエラーが出て、入力内容が残り、再投稿できる。
- タグ登録失敗時に投稿だけが残らない(確認方法は実装時に検討。例: 一時的に存在しない tag_id を送る)。
- CHECK 制約: SQL Editor などから501文字・空白のみの INSERT が拒否される。
- CHECK 制約追加後も、ホームの投稿編集(PostCard)とコメント投稿が従来どおり動く。
- スマホ幅(375px)でパネルとタグがはみ出さない。パネルが画面より高い場合にスクロールできる。
- ホーム・投稿詳細・プロフィールの表示が変わっていない(特に `.home-tag-button`)。
- `npm run lint` / `npm run build` が通る。

## 8. 実装時の注意点

- 本プロジェクトの Next.js は従来と仕様が異なる。実装前に `node_modules/next/dist/docs/` の該当箇所を確認する(`AGENTS.md`)。
- `app/globals.css`・`app/post/page.tsx` などに未コミットの変更がある。`.post-form*` は末尾追記とし、既存クラスは書き換えない。
- `.home-tag-button` はホームと共用になる。投稿画面の都合でこのクラス自体を変更しない(調整が必要なら `.post-form__tags` 側で行う)。
- 選択中のピル(白背景)は明るいパネル上で境界が弱くなる可能性がある。実機で見分けにくければ `.post-form__tags .home-tag-button.active` の範囲で調整する。
- **CHECK 制約の影響範囲**: `components/PostCard.tsx` の投稿編集には文字数上限がなく、失敗時に `alert(error.message)` で制約エラーの原文が出る。501文字以上に編集すると保存が失敗するようになる。PostCard 側の修正は今回の範囲外のため、別途対応が必要な事項として残る。
- 文字数の数え方: 画面の `maxLength` は UTF-16 単位、DB の `char_length` は文字単位。絵文字などでは画面側のほうが先に上限に達する(DB制約より厳しい側に倒れるので、画面を通った投稿が DB で拒否されることはない)。
- `user_id` は必ず `auth.getUser()` の値を使う。エラーの原文やユーザー情報を画面に出さない。

## 確定事項(ユーザー回答済み)

- 本文の上限は500文字。カウンターを表示する。
- タグはホームと同じピル型ボタン(画像のチェックボックスは採用しない)。
- DB変更は `posts.content` の CHECK 制約のみ。投稿とタグの登録は2段階のまま。
- 通知はパネル内表示。成功時は通知なしでホームへ遷移。

## 未確定・要確認事項(推測で実装しない)

1. パネルの透明度・入力欄の高さなどの細かい数値は画像からの目安。実機で画像と見比べて調整する。
2. タグ登録失敗時に投稿を取り消す挙動(3.2)は本方針の提案。「投稿は残してホームへ遷移する」現行挙動を維持したい場合は実装前に指定する。
3. 実DBの既存データが CHECK 制約に違反していないか、RLS が文書どおりか(5章)。
4. 画像の Header には Echo ロゴがないが、既存 Header を変更しない前提とした。
